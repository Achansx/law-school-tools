# Lessons

Append-only memory for the article-writing scheduled task. Read at the start of every run. Cap at 50 entries; if at cap, drop the entry with the lowest `impact_score`.

Schema per entry:

```
## L-NNN: <one-line title>
phase: <harvest | outline | draft | cite | polish | stitch | verify>
impact_score: <1-5>
date: YYYY-MM-DD
rule: <short imperative sentence the next run should obey>
context: <one paragraph: what went wrong, why, how this rule prevents it>
```

Lessons should be specific enough to act on and short enough to load every run.

## L-019: External bibliography URLs need Cite-phase verification, not Harvest

phase: harvest
impact_score: 4
date: 2026-05-16
rule: When a Harvest run cites an external URL from `Article-Workplan.md`'s annotated bibliography (arXiv, journal DOI, SSRN, archive.org), record `source_url` in the evidence card, mark `verified: false`, and name the deferred URL-liveness check in the card body. Do NOT retry WebFetch and do not score the card down on traceability. Scheduled-task runs cannot fetch URLs that appear only in vault files because WebFetch provenance gates URLs to user messages and prior fetch results. URL liveness is the Cite phase's job, mirroring how PI-005 handled the live wiki URL for Section 04.

context: Section 05's Harvest tick wrote two cards anchored to external arXiv URLs (Dong KG-RAG at arXiv:2311.17696, Peng GraphRAG at arXiv:2408.08921), both pulled from the workplan bibliography. Both URLs were refused by WebFetch with the provenance message that mirrors PI-005's pattern in Section 04. The workplan source itself is verified (the planning pass already read the underlying records), so the cards' factual content is fine; what is deferred is URL liveness, which belongs to the Cite phase regardless. Encoding this as a rule prevents future Harvest runs from retrying WebFetch, prevents traceability scores from being dinged for a verification that another phase owns, and keeps the Harvest output cleanly handed off to Cite when the section reaches that point in the rotation.

## L-020: Pending issues have an outline-addressed intermediate state

phase: outline
impact_score: 3
date: 2026-05-16
rule: When the Outline phase incorporates a candidate resolution to a Harvest-opened pending issue (for example, by binding a specific bullet to evidence that closes the gap), mark the pending_issue's `status` as `outline-addressed` with an `outline_addressed_at` timestamp; do NOT mark it `resolved` or `closed`. True closure requires the Draft phase to write the prose convincingly AND a subsequent Verify pass to accept the resolution. The intermediate state tells later phases that a candidate exists without falsely advertising that the gap is gone.

context: PI-011 (Section 05's second concrete iteration story for the reactive-schema claim) was provisionally addressed in the Outline run by naming the area-enum realignment alongside the token-problem-and-rubric-split story. Marking PI-011 as `resolved` would have lost the information that Draft and Verify still have to confirm the story carries the claim for a JLE audience; marking it `open` would have lost the information that the candidate is in the spine and Harvest should not re-pull. The schema's binary open/resolved state collapses too much. The `outline-addressed` intermediate makes the lifecycle legible: Harvest opens, Outline addresses, Draft writes, Cite/Polish refines, Verify accepts (true close) or rejects (back to open). Future Outline runs on later sections should adopt the same convention whenever a bullet leans on an open PI for closure.

## L-022: WebSearch is the URL-liveness path when WebFetch refuses by provenance

phase: cite
impact_score: 4
date: 2026-05-16
rule: When a Cite tick needs to verify a URL that appears only in a vault file (annotated bibliography, evidence card, RUNBOOK reference) and WebFetch refuses by provenance, run the URL through WebSearch instead. A returned title plus the verbatim URL in the search results counts as a live-URL confirmation sufficient to satisfy cite-rubric criterion 3 and to write the Bluebook footnote with a current last-visited date. WebFetch's provenance gate (a URL must appear in a user message or a prior fetch result to be fetched) cannot be worked around with retries, but WebSearch does not enforce the same gate. For URLs that WebSearch cannot confirm either, the L-019 deferral path still applies — log to pending_issues and let a later Cite or Verify tick resolve once provenance becomes available.

context: Section 05's Cite run faced two arXiv URLs (Dong et al. KG-RAG at arxiv.org/abs/2311.17696 and Peng et al. GraphRAG survey at arxiv.org/abs/2408.08921) that were marked `verified: false` by the Harvest run per the L-019 deferral protocol. WebFetch on either would have hit the same provenance refusal that produced PI-005 in Section 04. WebSearch resolved both URLs cleanly with title and verbatim URL returned in the first result. The cite rubric's URL-liveness criterion went from a likely 2 (the Section 04 Cite outcome) to a 5 on this run because of the substitution. Future Cite ticks on Sections VII, IX, X, XI, and XII, where external chatbot-tutor and AI-in-education literature gets cited from the workplan bibliography, should default to WebSearch for URL verification rather than WebFetch, and only fall back to deferral when WebSearch returns nothing. The lesson also retroactively names the resolution path for Section 04's PI-005 wiki URL: the next Cite tick on Section 04 should try WebSearch on https://constitutionallaw.netlify.app before flipping the footnote to an archive.org capture.

## L-024: Citation-transfer due diligence for AI-in-education literature in different intervention settings

phase: cite
impact_score: 4
date: 2026-05-17
rule: When the Cite or Polish phase imports an empirical claim (effect size, sample-statistic, comparative outcome) from an external AI-in-education study whose intervention setting differs from the case-study setting — for example, the case study is a static, reviewed website and the cited study is a chatbot-tutor with runtime retrieval — the cite or polish prose must include a one-sentence transfer clause naming what generalizes (the abstract structural insight: structure-aware retrieval beats flat semantic similarity; typed schemas beat unstructured prose) and what does not (the implementation surface: chatbot vs. static site, runtime vs. publish-time, conversational vs. browsable). Bluebook form alone is not enough. The transfer clause lives in body prose, not a footnote parenthetical, because the load-bearing inference is the article's claim and not the cited study's; an optional footnote parenthetical can name the intervention-setting difference for the reader who looks down.

context: Section V's Cite run produced clean Bluebook citations of Dong et al. KG-RAG (arXiv:2311.17696) and Peng et al. GraphRAG survey (arXiv:2408.08921), both verified live via WebSearch, both correctly anchored in V.D as external literature supporting the architectural choice. The 2026-05-17T03:00 Verify pass surfaced a P1 from both Persona 1 (Skeptical JLE Editor) and Persona 3 (AI-in-Education Researcher) on the same sentence: Dong et al.'s intervention is a chatbot-tutor with KG-RAG at runtime, while the vault is a static website with no runtime retrieval, so importing the Cohen's *d* = 0.86 effect size without a transfer clause sets up exactly the L-003 framing slip the article elsewhere disclaims (static, not chatbot) and the empirical-claim-without-methodology slip Persona 3's rubric watches for. The fix is a one-sentence insertion in V.D's third paragraph and can be made in the next Polish tick without re-running Cite, because the citation form itself is fine — what's missing is the transfer-of-inference framing in body prose. Future Cite ticks on Sections VII, IX, XI, XII, and XIII, where Bond et al.'s meta-review, Kuhail et al.'s chatbot-tutor survey, and other AI-in-higher-education literature will be cited, should add the transfer clause at Cite time rather than push the work to Polish, because the citation's load-bearing role is fully visible at the moment the footnote is constructed. Polish remains the safety net for misses, but the cleaner allocation matches L-015's "Cite owns Bluebook end-to-end" architecture, extended to "Cite owns the load-bearing transfer framing end-to-end" when the external study's intervention setting differs from the case-study setting. The lesson applies most strongly to chatbot-tutor literature (which is the closest cousin of the vault and the easiest framing slip), but it also applies to any pre/post within-subject study cited as evidence for a between-subjects implementation claim, any single-course pilot cited as evidence for institutional rollout, and any in-person classroom intervention cited as evidence for an asynchronous self-study setting.

## L-025: Harvest source-folder targeting depends on the section's type

phase: harvest
impact_score: 4
date: 2026-05-17
rule: Before walking vault sources for a section, classify the section as one of three types and pull primary evidence from the matching folder set. Vault-content sections (IV Input Corpus, V Obsidian Vault) pull from `Cases/`, `Topics/`, `Lectures/`, `Templates/`, `Source Materials/`, and `PROJECT_PRIMER.md`. Vault-infrastructure sections (VI Prompting, VII Iteration, VIII Vault-to-Website, IX Cost and Labor) pull from `.site/build.py`, `DEPLOY.md`, `RUNBOOK.md`, `LESSONS.md`, the `rubric/` folder, scheduled-task config, `BUILD_NARRATIVE_*` files, and `CHANGELOG.md`. Vault-framing sections (I Intro, II Why-Not-Casebook, X Generalization, XI Evaluation, XII Risks, XIII Institutional, XIV Conclusion) pull from `Article-Workplan.md`'s annotated bibliography (external URLs), the article's own thesis, and cross-references to the case-study sections. Mixing the layers wastes effort: searching `Cases/` for Section VIII evidence produces nothing useful, and searching `.site/` for Section IV evidence misses the content-layer facts the section actually argues from.

context: Section 08's Harvest run was the first to pull primary evidence from the vault's surrounding infrastructure rather than from vault content. The relevant files (DEPLOY.md, .site/build.py, .site/dist/netlify.toml, .site/dist/index.html) live outside the three content folders that Sections 04 and 05's Harvest runs walked. Without a section-type classification rule, future Harvest runs on Sections VI, VII, IX, and X risk either spending most of their time in the wrong folder or producing thin evidence sets because the right folder was not searched. The classification also makes the Harvest scoping decision repeatable: a future maintainer can read the rule and know which folders to walk for a section without reading the full PROJECT_PRIMER. The lesson does not override workplan-bibliography pulls (which apply across all section types when the workplan names an external source for a section) but it does name the default starting set so the run does not start from zero each time.

## L-027: Outline routes cost-table and audit-data line items to their owning section, not to the section that needs them

phase: outline
impact_score: 4
date: 2026-05-17
rule: When the Outline phase encounters a load-bearing claim that needs a specific numeric line item (a cost dollar figure, an audit count, a Netlify analytics number, a Bluebook URL-liveness date) whose ownership belongs to a different section per PROJECT_PRIMER or per the workplan's section-by-section commentary, the bullet must (a) name the qualitative architectural property the line item supports without quoting a fabricated number, and (b) route the numeric line item to its owning section by opening a pending_issue with the owner-section field set and an explicit closing condition. The Outline must not invent the number, must not push the fabrication risk onto Draft, and must not pretend the number is in the article when it lives in a section that has not yet drafted. The bullet's prose stays accurate and falsifiable; the missing number is logged where Harvest, Outline, or Draft on the owning section will pick it up.

context: Section 08's Outline tick faced this exact situation with PI-018 (the deploy-phase cost-table line). The 8.3 bullet on the Netlify CLI direct upload could have been written either as "the preferred CLI path uses zero Netlify build minutes" (qualitative architectural property, no number) or as "the preferred CLI path uses zero Netlify build minutes and runs in under five seconds per deploy at a typical token cost of $0.X per scheduled-task tick" (numeric line item invented at Outline time). The correct call was the first: the qualitative property is verified true from DEPLOY.md, the wall-clock and token-cost numbers belong to Section IX's cost-and-labor table per workplan §3.1, and pretending the numbers exist in Section VIII would force Section IX to either match a fabricated Section VIII figure or introduce an inter-section contradiction the Verify pass would catch. The same routing logic applies to: any Section III pull from the deployed site's analytics (Netlify page-view counts, search-term traces) that belong to Section XI's evaluation data; any Section V or VI mention of a Magesh hallucination percentage that belongs to Section XII's risk table; any Section IV or V token-spend reference that belongs to Section IX's cost table; any Section X or XIII generalization-cost estimate that belongs to Section IX. The convention keeps the article's numbers in one place per topic, prevents inter-section drift, and prevents the Outline-to-Draft handoff from carrying fabricated numbers into prose where the next Verify pass would have to catch them.

## L-028: Cite-tick surgical fix is independent of URL-liveness resolution when Verify routed a mixed-disclaimer P1 back to Cite

phase: cite
impact_score: 4
date: 2026-05-17
rule: When the Cite phase picks up a section whose `cite_status` was routed back to `needs_cite` by a Verify P1 against a mixed last-visited + deferred-liveness disclaimer pattern in a specific footnote, AND the underlying URL-liveness verification cannot be resolved this tick (WebSearch on the verbatim URL per L-022 returns no first-page match, and a follow-up WebSearch for an archive.org Wayback Machine capture returns no capture), the prose-side P1 is still independently fixable. Restructure the footnote to drop the mixed disclaimer pattern entirely: cite the substantive fact through its proper appendix or section pointer (App. A for case-study self-descriptive facts per L-014; App. D for personal-communication-adjacent material; another section's footnote for a URL whose primary anchor lives elsewhere), and let the URL persist in body prose at the section that names it as a primary fact (typically Section VIII for the deployed-site URL). The underlying PI (e.g., PI-005) stays open with the WebSearch and archive.org retries recorded in its note, and the URL-liveness verification waits for provenance to become available. Do not preserve the disclaimer pattern simply because the URL remains unverified; the prose surface must match the article's published-form standard even when verification still defers. Flip `cite_status` from `needs_cite` to `needs_polish` after the surgical fix so the next Polish tick on that section can pick up any remaining Polish-level P1s.

context: Section 04's footnote [^12] was Verify-P1'd on 2026-05-16T13:20 for the mixed last-visited + deferred-liveness disclaimer pattern the original Cite tick produced for https://constitutionallaw.netlify.app. The 2026-05-17T11:00 Cite tick attempted resolution per L-022: WebSearch on the verbatim URL returned ten other Netlify-hosted law sites but no verbatim match in the first page of results, and a follow-up WebSearch for an archive.org Wayback Machine capture of the URL returned only generic Wayback Machine documentation rather than a capture. Per L-022's tail clause the URL-liveness verification stays deferred under PI-005, but Verify's prose-side P1 is independently fixable, so the same Cite tick restructured [^12] to drop the disclaimer, cite the wiki-brief inventory through App. A's Missing-from-Export subsection, and cross-reference Section VIII.A note 1 where the deployed-site URL is the primary anchor fact carried by Section VIII's own Cite-phase work in the same tick. Section 04 advanced from `cite_status: needs_cite` to `cite_status: needs_polish` and the Cite-side half of the Verify routing is closed; the five Polish-level P1s (PI-006 through PI-010) wait for the next Polish tick. Without this rule, the Cite phase would either preserve the disclaimer (failing Verify's routing intent and recurring as the same P1 on the next Verify pass) or skip the section entirely (leaving `cite_status: needs_cite` indefinitely until URL provenance arrives). The pattern generalizes to any future Verify routing where the prose-side problem is a footnote-form issue and the URL-liveness verification is genuinely deferred — Cite cleans the prose, PI tracking carries the verification gap forward, and the next eligible tick continues the resolution path.

## L-031: Polish's voice-unity sweep includes a static-site-framing slip check, not only the explicit AI-tutor vocabulary check

phase: polish
impact_score: 4
date: 2026-05-17
rule: When a Polish tick runs the voice-unity sweep on any section that touches the deployed artifact, the published case study, or the static-vs-chatbot architectural distinction (presently Section IV, Section V, Section VIII; later Section II's gap-claim, Section XII's risk argument, Section XIII's institutional argument), the sweep must check for static-site-framing slips that anthropomorphize the deployed artifact as a conversational agent. The L-003 rule (never describe the case study as a chatbot, a tutor that converses, or an interactive assistant) extends from the explicit-vocabulary ban (no "AI tutor", no "conversational helper", no "interactive assistant") to a verb-and-metaphor ban: the published static site does not "talk back," does not "listen," does not "respond" except in the trivial HTTP-request sense, and does not "engage" the reader. Closed-loop feedback mechanisms (the Netlify page-feedback form, Step 0 intake, professor-feedback PI routing) are correctly described with named human actors carrying the verbs: the reader submits, the maintenance phase processes, the professor receives. Score Polish-rubric voice-consistency at 4 not 5 if the section under polish has any sentence that lets the static artifact carry a conversational verb, and route to PI tracking with the specific sentence quoted so the next Polish tick can land the fix.

context: Section 08's Polish tick (2026-05-17T13:00) scored voice_consistency at 5 because it caught and rewrote the "attorney-author" register slip in 8.2 and confirmed zero "AI tutor" framing slippage, but missed VIII.D's closing sentence "The published site talks back to the vault, and the vault routes the talk-back through the same rotation that produced the page." The 2026-05-17T17:00 Verify pass surfaced this as Persona 1's first P1 finding (PI-021) because the slip lives in the same section that goes hardest on the static-vs-chatbot distinction at VIII.E, which is exactly the framing contradiction a JLE peer reviewer reading VIII.D and VIII.E back-to-back will note. The L-003 rule as written before this lesson covered "chatbot," "tutor that converses," and "interactive assistant" by name, but did not catch personifying verbs and metaphors that achieve the same framing slip through different vocabulary. The fix is mechanical for the existing slip ("Reader feedback returns to the vault through the page-feedback form, and the next rotation phase processes each submission through the same pipeline that produced the page") and the rule prevention is mechanical for future Polish ticks: the voice-unity sweep adds a quick scan for personifying verbs attached to the deployed-site subject. Sections II, V, XII, and XIII will face the same risk by their nature — Section II contrasts ordinary LMS infrastructure against the case study (anthropomorphizing temptation high), Section V already mentions the deployed site once at V.B and once at V.D and could acquire a personifying verb during a future rewrite, Section XII is the article's central argument about why the static-site posture is the right architectural choice (slipping into chatbot-style framing there would be self-defeating), and Section XIII's institutional argument needs the static-vs-conversational distinction to ground the labor argument. Encoding the rule before those sections enter Polish prevents the same finding from recurring against each one. The lesson also clarifies that L-003 and L-031 are complementary, not duplicative: L-003 is the case-study self-description rule (never *call* the case study a chatbot); L-031 is the body-prose hygiene rule (never *let* the case study act like a chatbot through verbs and metaphors).

## L-032: Shared-asset gaps have a single owning section; downstream consumers route through the owner's PI

phase: harvest
impact_score: 4
date: 2026-05-17
rule: When multiple sections reference the same pending artifact (screenshots, figures, the cost-and-labor table, a survey-result table, a code listing, an interview excerpt), the Harvest phase identifies the section that owns the asset under PROJECT_PRIMER / workplan §3 commentary and opens a single master pending_issue against that owning section. Downstream consuming sections do NOT open their own pending issues for the same asset; instead, they reference the master PI by id and use the L-021 `[CITE: forward reference to Section N X figure; see PI-NNN-master]` convention to forward-cite. The master PI's note block enumerates every downstream consumer so future Harvest, Outline, Cite, and Stitch ticks can trace the dependency chain in one place. When the master PI closes (the asset lands), every downstream forward reference resolves in one Cite or Stitch pass rather than chasing per-section duplicate PIs. The owning-section convention also tells the Outline phase on the owning section to scope its image-capture or table-build session around the full downstream consumer list, not just the owning section's immediate needs.

context: Section 03's Harvest run faced the screenshot-set question directly. Section V's Harvest run had previously opened PI-012 against Section V for the holding-bar, graph-view, and four-family-grid figures, and Section VIII's Harvest run had previously opened PI-019 against Section VIII for the About page, ⌘K search palette with Marbury query, and page-feedback form open state. Capture these from constitutionallaw.netlify.app in a single session."). Section 03's Harvest run opened PI-027 as the master Section III screenshot capture gap, with the master list combining the workplan §3.2 six-image set plus the three Section-VIII-specific images from PI-019, and the PI-027 note enumerates PI-012 and PI-019 as downstream consumers whose forward references resolve when PI-027 closes. The alternative — three separate per-section PIs against the same screenshot session — would have produced three different capture windows that drift apart, three different Cite ticks that resolve forward references partially, and three different Stitch reconciliations to discover the drift; the single-owner convention prevents that. The lesson generalizes beyond screenshots: Section IX's cost-and-labor table is the same pattern (every cost line is owned by Section IX, and every other section that needs a cost figure forward-references through PI-018 rather than opening its own cost-PI per L-027); Section XI's evaluation data table will be the same; the Appendix B prompt library will be the same.

## L-034: Cross-section URL-verification reuse for closed PIs

phase: cite
impact_score: 3
date: 2026-05-17
rule: When a Cite tick on Section N cites the same external URL that an earlier Cite tick on Section M already verified live (via WebSearch or WebFetch) and whose tracking PI is closed, the Section N footnote reuses the Section M verification rather than re-running it, naming the verification date and method in a tail parenthetical that cross-references the Section M footnote (`URL liveness reused from Section M note Y (verified live on YYYY-MM-DD via WebSearch and a follow-up workspace fetch returning N characters of live response)`). The reuse is the cross-section analogue of L-014's case-study App.-A-pointer convention: a piece of verification work, once done, serves every section that depends on it. The convention applies only to closed PIs; for still-open PIs (e.g., PI-005 deferred under L-022/L-028), the deferral path still governs and no Section N reuse is available because no Section M verification exists yet. The tail parenthetical also creates an auditable chain for any Verify reader who wants to check the verification was actually performed somewhere upstream.
context: Section 03's Cite tick faced this exact pattern with the Sajja URL https://link.springer.com/article/10.1186/s41239-023-00412-7, which Section 08's 2026-05-17T11:00 Cite tick had already verified live via WebSearch with allowed_domains scoping and confirmed with a workspace web_fetch returning 89,771 characters (closing PI-020). Re-running the WebSearch on the same URL in the very next Cite tick on Section 03 would have produced the same result and wasted a tool call; ignoring the prior verification and pretending the URL still needed first-pass treatment would have invited per-section verification drift if the URL ever changed status between ticks. The cleaner allocation is the cross-reference: Section 03 footnote [^18] for Sajja reuses Section 08 note 15's verification, names the date and method, and locks the cite-rubric URL-liveness criterion 3 at 5 for the reused citation without per-section duplicate work. Future Cite ticks on Sections II, VI, VII, IX, X, XI, XII, and XIII that cite Sajja, Magesh, Karpathy's autoresearch repository, the Dong et al. KG-RAG paper, the Peng et al.
