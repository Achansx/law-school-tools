Successful upload and successful publication are different events; Section VIII can show the system distinguishes them with a structured post-deploy verification protocol. After the CLI reports `Deploy is live`, the procedure runs four sub-checks against the production CDN. First, manifest counts: `https://constitutionallaw.netlify.app/manifest.json` is fetched and its `meta.counts` for `case`, `topic`, `lecture`, and `total` are compared against the local `dist/manifest.json` that the build just wrote. Second, a page sample of five case briefs plus three topics is fetched via HTTP GET (deterministic sampling so replays are reproducible) and each response must return HTTP 200 and contain the expected page title in the body. Third, a search-sanity probe: the live `search.json` must include at least one entry whose title contains "Marbury" and whose text contains "judicial review" — Marbury is the canonical anchor of the corpus, so its absence signals an index regression. Fourth, a Source Materials sample: five raw PDFs or PowerPoints (selected from pages with non-empty `source_files`) are fetched via HTTP HEAD and must return HTTP 200 with the correct `Content-Type`. Each failure mode opens a typed pending issue (`deploy-count-mismatch`, `deploy-page-sample-failed`, `deploy-search-sanity-failed`, `deploy-source-sample-failed`) and blocks the state advance until the next successful Deploy resolves it. Section VIII can name this as the artifact-side complement to Section VII's source-side Verify discipline.

Exact source quote, `Chandler Constitutional Law Vault/DEPLOY.md` lines 90 to 98 (Step 3.5 expanded verification):

> **3.5a — Page sample (5 case briefs + 3 topics).** Pseudo-randomly pick 5 case-brief slugs and 3 topic slugs from the local `dist/manifest.json`. The selection MUST be deterministic per run (sort by slug, then take every Nth where N is `total / sample_size`) so the same run returns the same sample for replay. For each, issue an HTTP GET (not HEAD; SPAs sometimes return different status for the two) against `https://constitutionallaw.netlify.app/#/p/<id>`. Confirm HTTP 200 AND the response body contains the page title. Any non-200 response or any response missing its title becomes a `deploy-page-sample-failed` pending issue carrying `metadata.failed_sample` (a list of `{id, status, title_seen}` records).
>
> **3.5b — Search sanity ("Marbury" query).** Fetch `https://constitutionallaw.netlify.app/search.json` and confirm HTTP 200 with a non-empty `pages` array. Then perform a client-side text scan: confirm at least one entry whose `title` contains `Marbury` AND whose `text` contains the substring `judicial review`. "Marbury" is the canonical anchor case for the entire vault; if the live `search.json` cannot find it, the index is corrupt or the build silently truncated mid-write.
>
> **3.5c — Source Materials PDF sample (5 files).** Read `dist/manifest.json` once to get a list of pages with non-empty `source_files`. Pick 5 page entries (deterministic same-stride sampling), pull one Source Materials filename from each, and issue HEAD against `https://constitutionallaw.netlify.app/source/<url-encoded-filename>`. Confirm HTTP 200 AND a `Content-Type` of `application/pdf` (or `application/vnd.openxmlformats-officedocument.presentationml.presentation` for `.pptx`).
