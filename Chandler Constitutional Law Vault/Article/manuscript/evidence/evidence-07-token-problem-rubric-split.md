The article's second worked example of the loop is the token-problem story, which shows the loop reshaping its own architecture rather than catching a content error. Early runs loaded one large `RUBRIC.md` covering all six phases, the full `LESSONS.md` file, and the entire build narrative every pass, so a Lint run that only cared about structural formatting was burning context reading Enrich and Verify criteria it would never use. The fix was tiered loading: the rubric was split into per-phase files so each run loads only its own; the lessons file is loaded only by content-editing phases; the build narrative rotates monthly; and no-op phases stopped being scored at all. A secondary problem fell out of the same fix: a single shared rubric let one phase game a criterion in a way that made its own score look good while making another phase's job harder.

Exact source quote, `Chandler Constitutional Law Vault/archive/vault-blog-post-draft.md` lines 19 to 21:

> Early runs were expensive in a way that was not obvious at first. The system was loading everything every run: a single large RUBRIC.md covering all six phases, the full LESSONS.md, the entire build narrative, plus whatever files the current phase needed to process. A Lint run that only cares about structural formatting was burning context reading Enrich and Verify rubric criteria it would never use. A no-op Enrich run (nothing to enrich, corpus already caught up) was still loading the full lessons file, scoring itself, and appending to the narrative before concluding it had nothing to do.
>
> The fix was tiered loading. The RUBRIC.md was split into six per-phase files, so a Lint run loads only lint.md. The LESSONS.md is now skipped entirely by Lint and Verify unless a specific persona needs it. The build narrative rotates monthly so the file a run has to read stays bounded.
