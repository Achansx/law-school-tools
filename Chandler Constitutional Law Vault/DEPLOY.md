# Con Law Wiki Deploy

Mechanical procedure for the **Phase: Deploy** rotation step (see RUNBOOK "Phase: Deploy" for the rubric-facing description and `rubric/deploy.md` for scoring). This file is what the scheduled task reads when the dispatcher routes to `deploy`. Nothing below touches vault markdown.

## Entry guard

Run Deploy when ANY of the following holds at the start of the run, in this order:

1. `next_phase` in `.vault-maintenance-state.json` is `deploy` (the normal case after a clean Verify run).
2. `last_deploy` is missing entirely (first deploy or state file recreated).
3. Every one of `lint`, `enrich`, `expand`, `synthesize`, `verify` has a `phase_timestamps[<phase>]` entry strictly newer than `last_deploy` (cross-check by tailing `archive/phase-history-$(date -u +%Y-%m).jsonl` if a timestamp is missing).

If none holds, the dispatcher misrouted: log a `deploy-misrouted` pending issue with `applies_to_phase: deploy`, hand off to the next rotation phase, and end. Do not silently no-op.

If condition (1) holds but the most recent Verify run aborted (`personas-missing` or any unresolved high-severity finding), do NOT deploy. Log a `deploy-blocked-by-verify` pending issue and end. The cardinal rule from RUNBOOK applies: a stale live site beats a broken one in front of the professor.

## Files involved

- `.site/build.py` — Python builder that reads the vault and writes JSON to `.site/dist/`. Reads `VAULT_DIR` and `OUT_DIR` from the environment.
- `.site/dist/index.html`, `style.css`, `app.js`, `netlify.toml`, `_headers`, `_redirects` — static shell; do not regenerate, they are hand-written.
- `.site/dist/pages.json`, `manifest.json`, `search.json` — regenerated by every build.
- `.site/dist/source/` — `Source Materials/` mirrored under the dist tree so the deployed pages can serve raw PDFs and slide decks behind the `<a class="source-download">` links the build emits. Cleared and re-copied on every build via `shutil.rmtree(..., ignore_errors=True)` to survive iCloud quarantine on stale leftovers.
- `.site/.netlify-token` — Netlify PAT for the CLI fallback. Gitignored. Optional but strongly preferred (the MCP path uses build minutes; the CLI path with this token does not).
- `.site/deploy.sh` — wraps the CLI fallback. Exits 42 if the token is missing.

## Procedure

### Step 1 — Build

```bash
VAULT_DIR="/path/to/Chandler Constitutional Law Vault"
OUT_DIR="$VAULT_DIR/.site/dist"
pip install pyyaml markdown-it-py --break-system-packages -q
VAULT_DIR="$VAULT_DIR" OUT_DIR="$OUT_DIR" python3 "$VAULT_DIR/.site/build.py"
```

Exit code 0 and a printed `[build]` line with non-zero counts means success. On failure, log a `deploy-build-failed` pending issue (carry the stderr tail in `metadata.stderr_tail`), append a one-line CHANGELOG entry, leave `next_phase: deploy`, and end. Do NOT proceed to Step 2 with a broken build.

### Step 2 — Deploy

**Preferred path: Netlify CLI direct upload.** This is the canonical path because it does not consume Netlify build minutes and uses the local PAT, so deploys are reproducible from the scheduled task without proxy-token TTL pressure.

```bash
# Prime npx cache once per cold environment so the second invocation is instant.
npx -y netlify-cli@latest --version >/dev/null 2>&1 || true

cd "$VAULT_DIR/.site/dist"
NETLIFY_AUTH_TOKEN="$(cat "$VAULT_DIR/.site/.netlify-token")" \
  npx -y netlify-cli@latest deploy \
    --no-build \
    --prod \
    --dir . \
    --site f78a098b-9a9e-412a-8d4f-dd8ccda13bfe \
    --auth "$NETLIFY_AUTH_TOKEN"
```

Capture the CLI output. It prints lines of the form `Uploading X files of Y` (used for the `content_hash_incremental_hit_rate` rubric criterion) and a final `Deploy is live` line with the production URL.

If the PAT file is missing, do NOT silently fall through: log a `deploy-token-missing` pending issue carrying the path that was checked (`$VAULT_DIR/.site/.netlify-token`) and proceed to the MCP fallback.

**Fallback path: Netlify MCP.** Call `netlify-deploy-services-updater` with `operation: deploy-site` and `siteId: f78a098b-9a9e-412a-8d4f-dd8ccda13bfe`. The response returns an `npx @netlify/mcp` command embedded with a short-lived proxy path token. Run that command from `$VAULT_DIR/.site/dist` within the same scheduled-task run (the proxy token has a short TTL). This consumes Netlify build minutes; restore the PAT as soon as possible to drop back to the preferred path.

**Last-resort fallback: `deploy.sh`.** If the PAT is present but the CLI invocation above fails for an environment-specific reason (npx cache wedged, PATH issue), fall back to:

```bash
bash "$VAULT_DIR/.site/deploy.sh"
```

This script does its own build, so do not run Step 1 first if you are taking this fallback.

### Step 3 — Verify deploy

Fetch `https://constitutionallaw.netlify.app/manifest.json` and confirm HTTP 200 with a non-empty JSON body whose `meta.counts` matches the local `dist/manifest.json` written by Step 1 on every key (`case`, `topic`, `lecture`, `total`).

Mismatch on any key: log a `deploy-count-mismatch` pending issue carrying `metadata.local_counts` and `metadata.live_counts`. Treat the deploy as failed: leave `next_phase: deploy` so next cycle retries. The build cached a stale vault, the upload was partial, or the live CDN is stuck on a prior version.

Also confirm the Netlify deploy record reached the `ready` state. If the CLI printed `Deploy is live` but a quick HTTP HEAD on a representative page (for example `https://constitutionallaw.netlify.app/`) does not return 200, treat the deploy as a `deploy-zombie`: log the deploy ID in `metadata.deploy_id` and leave `next_phase: deploy`.

### Step 3.5 — Expanded verification (page sample, search sanity, source sample)

Manifest counts proved the right number of pages were published, but that check passes even if the page bodies are 404 placeholders or `search.json` regressed. The three sub-checks below catch those failure modes cheaply by sampling the live CDN.

**3.5a — Page sample (5 case briefs + 3 topics).** Pseudo-randomly pick 5 case-brief slugs and 3 topic slugs from the local `dist/manifest.json`. The selection MUST be deterministic per run (sort by slug, then take every Nth where N is `total / sample_size`) so the same run returns the same sample for replay. For each, issue an HTTP GET (not HEAD; SPAs sometimes return different status for the two) against `https://constitutionallaw.netlify.app/#/p/<id>`. Confirm HTTP 200 AND the response body contains the page title. Any non-200 response or any response missing its title becomes a `deploy-page-sample-failed` pending issue carrying `metadata.failed_sample` (a list of `{id, status, title_seen}` records). Treat it like a count mismatch: leave `next_phase: deploy`. The case-brief share is weighted higher (5 vs. 3) because they are the bulk of the corpus and the more common failure surface.

**3.5b — Search sanity ("Marbury" query).** Fetch `https://constitutionallaw.netlify.app/search.json` and confirm HTTP 200 with a non-empty `pages` array. Then perform a client-side text scan: confirm at least one entry whose `title` contains `Marbury` AND whose `text` contains the substring `judicial review`. "Marbury" is the canonical anchor case for the entire vault; if the live `search.json` cannot find it, the index is corrupt or the build silently truncated mid-write. Failure: log `deploy-search-sanity-failed` carrying `metadata.entries_seen` (count) and `metadata.marbury_match` (bool). Leave `next_phase: deploy`.

**3.5c — Source Materials PDF sample (5 files).** Read `dist/manifest.json` once to get a list of pages with non-empty `source_files`. Pick 5 page entries (deterministic same-stride sampling), pull one Source Materials filename from each, and issue HEAD against `https://constitutionallaw.netlify.app/source/<url-encoded-filename>`. Confirm HTTP 200 AND a `Content-Type` of `application/pdf` (or `application/vnd.openxmlformats-officedocument.presentationml.presentation` for `.pptx`). Any failure becomes `deploy-source-sample-failed` carrying `metadata.failed_sample` ({filename, status, content_type}). The source folder is gigabytes; if it silently dropped during upload the manifest counts still pass but every download link is dead, so this check is the cheapest way to catch that class of regression.

All three sub-checks run AFTER the manifest count check passes and BEFORE Step 4 advances `last_deploy`. A failure in any of 3.5a / 3.5b / 3.5c blocks the state advance just like a manifest mismatch does. Capture the wall-clock cost of all three in the run summary; the budget is roughly 10 to 15 seconds total (8 GETs + 1 search.json fetch + 5 HEADs against a CDN).

### Step 4 — Update state

On a Step 3 pass, set `last_deploy` in `.vault-maintenance-state.json` to the ISO-8601 timestamp of Step 3's manifest-verify completion. Confirm the new value is strictly newer than its prior value AND newer than every `phase_timestamps[<phase>]` value for this rotation's content phases (lint, enrich, expand, synthesize, verify). If the write appears to have skipped (equal or older value on re-read), log a `deploy-state-not-advanced` pending issue carrying the attempted timestamp.

Append a one-line `CHANGELOG.md` entry:

```
YYYY-MM-DDThh:mm:ssZ  deploy  counts={case,topic,lecture}  url=constitutionallaw.netlify.app  hit_rate=<X/Y>
```

Include the incremental hit rate (Y - X over Y from the CLI's `Uploading X files of Y` line) so the next Deploy run can spot a sudden drop without re-parsing logs.

Set `next_phase` to whichever rotation phase comes after Deploy in the cycle (back to Lint at the start of the next rotation, or to whatever the dispatcher's natural next step is). Do this only after Steps 1 to 3 succeeded; if any step failed, `next_phase: deploy` stays put for retry.

### Step 5 — Score

Open `rubric/deploy.md`, compute raw 0-to-5 scores for all five criteria using the data captured in the previous steps (CLI hit-rate line, wall-clock from build start to manifest-verify end, Step 3 result, Step 4 state-write result, zombie check). Compute the weighted average and append one JSON line to `.run-scores.jsonl`.

If the score sits more than 1.0 below the rolling median of the last five Deploy runs, add `regression-vs-median` to red flags and surface in the run summary.

## Pending-issue lifecycle (Deploy owns its own)

Deploy opens issues with `applies_to_phase: deploy` and closes them itself on the next successful Deploy run. They never wait for Lint or Verify to pick them up. Standard issue types:

- `deploy-build-failed` — Step 1 returned non-zero. `metadata.stderr_tail`.
- `deploy-token-missing` — `.site/.netlify-token` not present. `metadata.path_checked`.
- `deploy-count-mismatch` — Step 3 manifest verification failed. `metadata.local_counts`, `metadata.live_counts`.
- `deploy-zombie` — Deploy record created but never reached `ready`. `metadata.deploy_id`.
- `deploy-state-not-advanced` — `last_deploy` did not advance despite an apparently successful deploy. `metadata.attempted_timestamp`.
- `deploy-misrouted` — Dispatcher routed here when no entry-guard condition held.
- `deploy-blocked-by-verify` — Verify aborted or left a high-severity finding open.
- `deploy-page-sample-failed` — Step 3.5a sample of 5 case briefs + 3 topics returned at least one non-200 or title-missing. `metadata.failed_sample`.
- `deploy-search-sanity-failed` — Step 3.5b "Marbury" sanity probe found no matching entry. `metadata.entries_seen`, `metadata.marbury_match`.
- `deploy-source-sample-failed` — Step 3.5c sample of 5 Source Materials downloads returned at least one non-200 or wrong Content-Type. `metadata.failed_sample`.

When a Deploy retry succeeds and the underlying condition is gone, close the prior issue inline and note the close in the run's CHANGELOG entry. If three consecutive Deploy runs hit the same issue type, escalate by appending a `deploy-recurring-failure` lesson candidate to `pending_issues` for the next Consolidate sweep — `rubric/deploy.md` defines the escalation criteria.

## Cardinal rules

- Never deploy a build that did not finish cleanly.
- Never modify `.site/dist/*.json` by hand — they are artefacts.
- Never delete `.site/dist/index.html`, `style.css`, or `app.js` — they are source and only humans edit them.
- Never commit the Netlify auth token; only `.netlify-token` (gitignored), the MCP flow, or an ambient `NETLIFY_AUTH_TOKEN` env var is allowed.
- Never advance `next_phase` past Deploy unless Steps 1 through 4 all succeeded. A failed phase stays as the next phase.
